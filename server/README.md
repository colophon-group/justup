# Demo API

This directory serves a bounded public Jobseek snapshot through same-origin `/api/v1` routes and composes invite-only authentication from `auth.mjs`. It uses Node.js **24.22.2**, built-in HTTP/crypto/SQLite and no application packages. SQLite belongs only to the isolated demo; no database service, production database, billing, mail or crawler writes are used. The [data guide](../docs/demo-job-data.md) describes the explicit public import command. The auth module must be present before direct execution; it has separate ownership and tests.

Run focused tests with `node --test server/*.test.mjs` and `python3 -m unittest discover -s scripts -p 'test_import_demo_jobs.py'`. The core suite owns access/freshness, public projections, cursors, task leases, HTTP security and service composition. It uses fixed clocks, isolated SQLite and local fake services, completes in under one second locally and makes no public requests. The auth suite owns password verification. CI registers these server paths separately from browser journeys.

## Start or import

Set `JUSTUP_DEMO_DB_PATH` to an isolated SQLite file and `JUSTUP_DEMO_ORIGIN` to the exact allowed browser HTTPS origin, then run `node server/main.mjs`. Authentication additionally requires the auth module’s synchronous retention cleanup to be available and successful, plus the deletion barrier below. The `/session` response explicitly reports `authentication.loginEnabled`, `registrationEnabled`, `method` and safe unavailable reasons. Model outages affect feature capabilities without preventing login or account deletion.

It binds `127.0.0.1` on `JUSTUP_DEMO_PORT` (default 8787). A reverse proxy must keep the browser's API same-origin. Private local storage uses a restrictive umask and mode-0600 database. The reviewed shared preview uses `JUSTUP_DEMO_SHARED_STATE=true`, process umask `0007`, and an existing root-created setgid `02770` state directory; database, WAL and SHM files are `0660`. Only the API and queue UIDs belong to its state group. The model UID has no database access. Shared startup rejects a different directory mode or umask and does not create or change group ownership. Runtime secret files remain owner-only `0600`. The explicit `JUSTUP_DEMO_ALLOW_LOCAL_HTTP=true` option permits local HTTP only for localhost or loopback testing.

Registration requires `JUSTUP_DEMO_INVITE_CODE`. Both registration and login stay closed until these are configured: `JUSTUP_DEMO_POLICIES_REVIEWED=true`, approved HTTPS `JUSTUP_DEMO_PRIVACY_URL` and `JUSTUP_DEMO_USAGE_URL`, and `JUSTUP_DEMO_POLICY_VERSION`. This is a reviewed deployment decision; setting a flag does not itself constitute policy approval. Policy pages are static frontend routes. There is no policy JSON API.

Set immutable `JUSTUP_DEMO_SOURCE_COMMIT` and `JUSTUP_DEMO_BUILD_ID` for version reporting. Supply stable random secrets of at least 32 bytes as `JUSTUP_DEMO_CSRF_SECRET` and `JUSTUP_DEMO_CURSOR_SECRET` through the protected preview runtime; never put values in commands, Git or a frontend bundle. Omitted secrets are process-local random values, suitable for isolated tests; restarting invalidates existing cursors and CSRF tokens until the next session read. Use the [credential guide](../docs/secrets.md) for runtime delivery.

Load an already reviewed private export with `node server/main.mjs --import /private/demo-data/snapshot.json` using the explicit demo database path and shared-state option where applicable. This operation opens only the public snapshot store and does not create authentication, run account cleanup or omit domain deletion hooks. This command prints only counts and a random import generation, then exits. It does not fetch, schedule, transfer or deploy anything. Import files are at most 64 MiB, each body at most 512 KiB, and the store retains at most 1,000 jobs plus 32 bounded import summaries. SQLite has a 1 GiB page ceiling; preview disk and aggregate process/resource enforcement belongs to the deployment contract. Keep storage and exports outside Git; `.demo/` and SQLite files are ignored as a local fallback. Preserve source discovery times: a changed first-observed time for an existing source ID rejects the transaction.

Jobs older than 14 days or with verification older than 24 hours are suppressed independently. Visitors receive only the 48-hour–14-day slice. Accounts receive eligible jobs within 14 days. Explicit inactive observations record when closure was observed; missing/failed refreshes remain unknown. Source descriptions and evidence hashes are internal only. Public DTOs expose structured fields and original links; the company catalogue does not infer official domains or claim board monitoring.

## Extend the API

`await createDemo({config, now, serviceFactories, authFactory, logger})` returns `{server,store,feed,tasks,auth,services,close}`. `authFactory` is an isolated-test seam; normally it imports `createAuth` from `auth.mjs`. Each synchronous feature factory receives `{db,feed,tasks,config,now,beforePrivateDelete,afterPrivateTransaction,withPrivateTransaction}` and returns one service or an array. A service may implement:

- `capabilities`: object or zero-argument function reporting actual availability.
- `route(ctx)`: async or synchronous; return `{status,body}` when handled or null/undefined otherwise.
- `taskResult(task,ctx)`: return the safe accepted search/request or warning for its own task kind, undefined for other kinds. Return exactly one key: `{search}`, `{request}` or `{proposal}`. The public envelope is `{id,kind,status,createdAt,updatedAt,result,error}`; pending/running have null result/error, and failed tasks have a redacted `{code,message,retryable}` error. Raw task output is never exposed automatically. Do not place job DTOs or raw provider output in task responses.
- `deleteAccountData(ownerId)`: synchronous private cleanup inside the auth transaction, without another transaction or asynchronous work.

The route context is `{method,path,url,body,viewer,accountId,requestId,db,idempotencyKey}`. `idempotencyKey` is null or the validated `Idempotency-Key` header (1–128 ASCII token characters); company acceptance must not substitute a body field for this header. `path` excludes `/api/v1`; `url` is a URL object. `viewer` is `auth.session(token)` with `{account:{id,username},expiresAt,access}`, or null. Private feature routes always receive a signed-in viewer; ownership comes from `accountId`. Mutation Origin, CSRF, rate and JSON checks run centrally before a service executes. Services must recheck domain authorization, revisions and limits. Feature errors use reviewed safe codes; unrecognized errors become a generic 500. No exception message or provider output reaches the browser or diagnostic logger.

`feed.eligibleJobs({viewer})` supplies internal eligible evidence in source-time descending, ID ascending order. Recheck it for every result page. `feed.publicJob(job)` is the allowlisted browser projection. `feed.list` cursors bind evidence generation, guest/account access and a ten-minute lifetime. The public company methods contain only imported identity/evidence. `coverage()` reports imported snapshot verification and staleness, never an unsupported coverage claim or hidden count.

`tasks.enqueue({ownerId,kind,requestKey,payload})` returns the existing task for an exact retry; a changed payload with the same owner/kind/key conflicts. Payloads are at most 16 KiB, output at most 64 KiB, at most 96 tasks exist and at most four pending/running tasks belong to one account. Terminal rows expire after 30 days when enqueuing. `claim({workerId,kinds,leaseMs})` allows one global running task and returns `leaseToken`; leases are 1–300 seconds. `heartbeat(id,leaseToken,leaseMs)` and `complete(id,leaseToken,{status,output,errorCode})` compare the live lease and return a boolean. Complete statuses are succeeded/warning/failed. `recover()` retries expired leases up to three attempts, then records safe terminal failure. Safe provider-down, timeout and rate-limit task errors have `retryable:true`; validation errors and unknown codes are not retryable. A worker must check lease ownership and resource/time limits before committing domain effects in the same database transaction. The queue alone does not make an external provider call exactly once.

`tasks.get(ownerId,id)` is internal and returns null for a different owner. `publicView(task,safeResult)` strips payload, raw output and lease details. `delete(ownerId,id)`, `cancel(ownerId,id)`, `cancelOwner(ownerId)` and `deleteOwner(ownerId)` deliberately open no transactions and invalidate late completion. The feature deletion hooks and task deletion compose with auth deletion atomically.

Health reports process readiness and a separate runner availability state. The core has no runner: its default runner identity is null and readiness false. Integrations inject `config.readiness()` and feature capabilities from the actual bounded runner/provider, and must verify them before release. `/version` reports source commit, schema version, immutable build identity, runner and import generation; missing values are null, never fabricated identities. SSE, follows, viewed state, preferences, hidden counts and Hiring Wire remain false.

Diagnostics are optional metadata-only callbacks: request ID, route category, status and duration. There is no raw query/body/IP/token logging. Abuse keys are ephemeral HMACs of the direct socket peer, with a bounded map and minute windows; forwarded headers are ignored. A reverse proxy needs its own trusted per-client limits so shared ingress cannot erase the effective user boundary. No durable diagnostic log or model trace is created by core code.

## Private deletion and recovery

Persistent previews require precreated mode-0700 state and dedicated flat backup directories. Set `JUSTUP_DEMO_PRIVATE_GENERATION_PATH` to the live UUID-plus-newline generation file and `JUSTUP_DEMO_BACKUP_DIR` to the dedicated backup directory. The API does not create these recovery directories. The generation file cannot be inside the backup directory, and neither can the live database. Symlinks, nested directories and nonregular backup entries fail closed. With missing or unwritable recovery state, login and registration remain unavailable.

Before private deletion, the transaction owner creates `private-generation.pending` exclusively with mode `0600`, containing a version and random ownership token. It fsyncs the marker and state directory **before** rotating the generation. The marker remains present throughout the actual SQLite commit or rollback. The barrier then writes a new generation through a mode-0600 exclusive temporary file, fsyncs it, renames it over the live generation and fsyncs its parent; it purges the dedicated old backup files and fsyncs their directory. Generation rotation alone is insufficient: a concurrent SQLite backup can still contain pre-deletion rows until the writer commits.

Feature DELETE routes use `withPrivateTransaction(syncFunction)` and call `beforePrivateDelete()` inside the function before private SQL deletes. The wrapper commits or rolls back, then invokes `afterPrivateTransaction()`. Never await inside a database transaction. Account hooks remain synchronous inside auth's transaction; they never clear the marker themselves. HTTP completion/finally and auth maintenance call `afterPrivateTransaction()` only after the auth-owned transaction ends. Marker cleanup refuses while `db.isTransaction` is true and checks the marker's regular-file identity and ownership token before unlinking and fsyncing the state directory. It never clears another process's marker. A crash-retained or replaced marker fails closed and requires an explicit operator recovery decision; startup does not automatically erase it.

Backup and restore consumers must make a stable generation read with no pending marker both before and after taking or accepting the SQLite snapshot: generation read 1, require no pending marker, generation read 2, require equality. They reject missing or mismatched generations, and never restore the live generation or pending marker. A retained pre-deletion backup fails against the rotated live generation. Tests also copy the real SQLite database from a second process during an uncommitted deletion: that copy still contains the old private row and the new generation, while the pending marker correctly causes both consumer checks to reject it.

The explicit `node server/main.mjs --prepare-restored-db /private/restored.sqlite` command rejects the live database path and calls the auth-owned `invalidateAllSessions()` helper on the separate restored file. It prints `{schemaVersion:1,sessionsInvalidated:true,remainingSessions:0,sessionsDeleted}`. Only `JUSTUP_DEMO_DB_PATH` (the live-path guard) is required; no runtime credentials, browser origin, feature services or account-retention cleanup run during preparation. It cannot restore a backup or its generation. Normal fully composed runtime startup invokes auth `cleanup()` once per minute with all feature deletion hooks; failures close authentication availability until a successful retry.

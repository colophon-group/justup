# Demo API

This directory serves a bounded public Jobseek snapshot through same-origin `/api/v1` routes and composes invite-only authentication from `auth.mjs`. It uses Node.js **24.22.2**, built-in HTTP/crypto/SQLite and no application packages. SQLite belongs only to the isolated demo; no database service, production database, billing, mail or crawler writes are used. The [data guide](../docs/demo-job-data.md) describes the explicit public import command. The auth module must be present before direct execution; it has separate ownership and tests.

Run focused tests with `node --test server/*.test.mjs` and `python3 -m unittest discover -s scripts -p 'import_demo_jobs_test.py'`. The core suite owns access/freshness, public projections, cursors, task leases, HTTP security and service composition. It uses fixed clocks, isolated SQLite and local fake services, completes in under one second locally and makes no public requests. The auth suite owns password verification. CI registers these server paths separately from browser journeys.

## Start or import

Set `JUSTUP_DEMO_DB_PATH` to an isolated SQLite file and `JUSTUP_DEMO_ORIGIN` to the exact allowed browser HTTPS origin, then run `node server/main.mjs`. Authentication additionally requires the auth module’s synchronous retention cleanup to be available and successful, plus the deletion barrier below. The `/session` response explicitly reports `authentication.loginEnabled`, `registrationEnabled`, `method` and safe unavailable reasons. Model outages affect feature capabilities without preventing login or account deletion.

It binds `127.0.0.1` on `JUSTUP_DEMO_PORT` (default 8787). A reverse proxy must keep the browser's API same-origin. The dedicated process uses a restrictive umask and a mode-0600 database. The explicit `JUSTUP_DEMO_ALLOW_LOCAL_HTTP=true` option permits local HTTP only for localhost or loopback testing.

Registration requires `JUSTUP_DEMO_INVITE_CODE`. Both registration and login stay closed until these are configured: `JUSTUP_DEMO_POLICIES_REVIEWED=true`, approved HTTPS `JUSTUP_DEMO_PRIVACY_URL` and `JUSTUP_DEMO_USAGE_URL`, and `JUSTUP_DEMO_POLICY_VERSION`. This is a reviewed deployment decision; setting a flag does not itself constitute policy approval. Policy pages are static frontend routes. There is no policy JSON API.

Set immutable `JUSTUP_DEMO_SOURCE_COMMIT` and `JUSTUP_DEMO_BUILD_ID` for version reporting. Supply stable random secrets of at least 32 bytes as `JUSTUP_DEMO_CSRF_SECRET` and `JUSTUP_DEMO_CURSOR_SECRET` through the protected preview runtime; never put values in commands, Git or a frontend bundle. Omitted secrets are process-local random values, suitable for isolated tests; restarting invalidates existing cursors and CSRF tokens until the next session read. Use the [credential guide](../docs/secrets.md) for runtime delivery.

Load an already reviewed private export with `node server/main.mjs --import /private/demo-data/snapshot.json` using the same explicit demo configuration. This command prints only counts and a random import generation, then exits. It does not fetch, schedule, transfer or deploy anything. Import files are at most 64 MiB, each body at most 512 KiB, and the store retains at most 1,000 jobs plus 32 bounded import summaries. SQLite has a 1 GiB page ceiling; preview disk and aggregate process/resource enforcement belongs to the deployment contract. Keep storage and exports outside Git; `.demo/` and SQLite files are ignored as a local fallback. Preserve source discovery times: a changed first-observed time for an existing source ID rejects the transaction.

Jobs older than 14 days or with verification older than 24 hours are suppressed independently. Visitors receive only the 48-hour–14-day slice. Accounts receive eligible jobs within 14 days. Explicit inactive observations record when closure was observed; missing/failed refreshes remain unknown. Source descriptions and evidence hashes are internal only. Public DTOs expose structured fields and original links; the company catalogue does not infer official domains or claim board monitoring.

## Extend the API

`await createDemo({config, now, serviceFactories, authFactory, logger})` returns `{server,store,feed,tasks,auth,services,close}`. `authFactory` is an isolated-test seam; normally it imports `createAuth` from `auth.mjs`. Each synchronous feature factory receives `{db,feed,tasks,config,now,beforePrivateDelete}` and returns one service or an array. A service may implement:

- `capabilities`: object or zero-argument function reporting actual availability.
- `route(ctx)`: async or synchronous; return `{status,body}` when handled or null/undefined otherwise.
- `taskResult(task,ctx)`: return the safe accepted search/request or warning for its own task kind, undefined for other kinds. Return exactly one key: `{search}`, `{request}` or `{proposal}`. The public envelope is `{id,kind,status,createdAt,updatedAt,result,error}`; pending/running have null result/error, and failed tasks have a redacted `{code,message,retryable:false}` error. Raw task output is never exposed automatically. Do not place job DTOs or raw provider output in task responses.
- `deleteAccountData(ownerId)`: synchronous private cleanup inside the auth transaction, without another transaction or asynchronous work.

The route context is `{method,path,url,body,viewer,accountId,requestId,db}`. `path` excludes `/api/v1`; `url` is a URL object. `viewer` is `auth.session(token)` with `{account:{id,username},expiresAt,access}`, or null. Private feature routes always receive a signed-in viewer; ownership comes from `accountId`. Mutation Origin, CSRF, rate and JSON checks run centrally before a service executes. Services must recheck domain authorization, revisions and limits. Feature errors use reviewed safe codes; unrecognized errors become a generic 500. No exception message or provider output reaches the browser or diagnostic logger.

`feed.eligibleJobs({viewer})` supplies internal eligible evidence in source-time descending, ID ascending order. Recheck it for every result page. `feed.publicJob(job)` is the allowlisted browser projection. `feed.list` cursors bind evidence generation, guest/account access and a ten-minute lifetime. The public company methods contain only imported identity/evidence. `coverage()` reports imported snapshot verification and staleness, never an unsupported coverage claim or hidden count.

`tasks.enqueue({ownerId,kind,requestKey,payload})` returns the existing task for an exact retry; a changed payload with the same owner/kind/key conflicts. Payloads are at most 16 KiB, output at most 64 KiB, at most 96 tasks exist and at most four pending/running tasks belong to one account. Terminal rows expire after 30 days when enqueuing. `claim({workerId,kinds,leaseMs})` allows one global running task and returns `leaseToken`; leases are 1–300 seconds. `heartbeat(id,leaseToken,leaseMs)` and `complete(id,leaseToken,{status,output,errorCode})` compare the live lease and return a boolean. Complete statuses are succeeded/warning/failed. `recover()` retries expired leases up to three attempts, then records safe terminal failure. A worker must check lease ownership and resource/time limits before committing domain effects in the same database transaction. The queue alone does not make an external provider call exactly once.

`tasks.get(ownerId,id)` is internal and returns null for a different owner. `publicView(task,safeResult)` strips payload, raw output and lease details. `delete(ownerId,id)`, `cancel(ownerId,id)`, `cancelOwner(ownerId)` and `deleteOwner(ownerId)` deliberately open no transactions and invalidate late completion. The feature deletion hooks and task deletion compose with auth deletion atomically.

Health reports process readiness and a separate runner availability state. The core has no runner: its default runner identity is null and readiness false. Integrations inject `config.readiness()` and feature capabilities from the actual bounded runner/provider, and must verify them before release. `/version` reports source commit, schema version, immutable build identity, runner and import generation; missing values are null, never fabricated identities. SSE, follows, viewed state, preferences, hidden counts and Hiring Wire remain false.

Diagnostics are optional metadata-only callbacks: request ID, route category, status and duration. There is no raw query/body/IP/token logging. Abuse keys are ephemeral HMACs of the direct socket peer, with a bounded map and minute windows; forwarded headers are ignored. A reverse proxy needs its own trusted per-client limits so shared ingress cannot erase the effective user boundary. No durable diagnostic log or model trace is created by core code.

## Private deletion and recovery

Persistent previews require precreated mode-0700 state and dedicated flat backup directories. Set `JUSTUP_DEMO_PRIVATE_GENERATION_PATH` to the live UUID-plus-newline generation file and `JUSTUP_DEMO_BACKUP_DIR` to the dedicated backup directory. The API does not create these recovery directories. The generation file cannot be inside the backup directory, and neither can the live database. Symlinks, nested directories and nonregular backup entries fail closed. With missing or unwritable recovery state, login and registration remain unavailable.

Before account deletion commits, the synchronous barrier writes a new random generation to a mode-0600 exclusive temporary file, fsyncs it, renames it over the live generation and fsyncs its parent. It then removes every old regular backup file and fsyncs that directory. Barrier failure throws and rolls back private SQL changes; a later SQL failure can leave a rotated generation, safely invalidating extra old backups. Individual feature deletion routes must call the injected `beforePrivateDelete()` inside their transaction before removing private rows. Their account-deletion hooks do not repeat the barrier, since the account hook already invokes it once.

Backup/restore tooling must bind a snapshot to the generation observed before and after creation, reject missing or mismatched live generations, and never restore the live generation file. The explicit `node server/main.mjs --prepare-restored-db /private/restored.sqlite` command rejects the live database path and calls the auth-owned `invalidateAllSessions()` helper on the separate restored file. It prints a receipt `{schemaVersion:1,sessionsInvalidated:true,remainingSessions:0,sessionsDeleted}`; the final count comes from the auth-owned helper. Only `JUSTUP_DEMO_DB_PATH` (the live-path guard) is required for preparation; no runtime credentials or browser origin are needed. Restore remains blocked if that helper is absent. No SQL belonging to auth is guessed by core or operations tooling. The auth `cleanup()` hook runs at startup and once per minute to enforce its retention contract; failures close authentication availability until a successful retry.

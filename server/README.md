# Justup API

This directory serves attributable Jobseek imports through same-origin `/api/v1` routes and composes durable local accounts from `auth.mjs`. It uses Node.js **24.22.2**, built-in HTTP/crypto/SQLite and no application packages. The API, one leased queue runner and private model broker form the product runtime. Invitation admission, temporary account policy and preview resource limits are deployment configuration. The [data guide](../docs/job-data.md) describes the explicit bounded importer; continuous refresh still needs its launch integration. Billing, mail and crawler writes are not implemented.

Run focused tests with `node --test server/*.test.mjs` and `python3 -m unittest discover -s scripts -p 'test_import_jobs.py'`. The core suite owns access/freshness, public projections, cursors, task leases, HTTP security and service composition. It uses fixed clocks, isolated SQLite and local fake services, completes in roughly 15 seconds locally including password hashing and makes no public requests. The auth suite owns password verification. The reading-preferences suite owns follow/locale compare-and-set, search-option filtering and revision fences, canonical request publication, deletion/reopen and local HTTP handoff; it normally takes a few seconds with no external providers. CI recursively discovers these adjacent server contracts separately from browser journeys.

## Start or import

The application database epoch is 2. Empty storage initializes it atomically; existing epoch-1 storage is refused until an explicit offline migration. Read the [schema and forward-recovery guide](../docs/schema.md) before changing stored names or reusing an existing database. `schema.mjs` owns the epoch and one migration; feature modules continue to own additive table initialization. Its disk-backed suite covers populated legacy state, process interruption, mixed/corrupt state and preserved identity/spend.

Set `JUSTUP_DB_PATH` to the application SQLite file and `JUSTUP_ORIGIN` to the exact allowed browser HTTPS origin, then run `node server/main.mjs`. Authentication additionally requires the auth module’s synchronous retention cleanup to be available and successful, plus the deletion barrier below. The `/session` response explicitly reports `authentication.loginEnabled`, `registrationEnabled`, `method` and safe unavailable reasons. Model outages affect feature capabilities without preventing login or account deletion.

It binds `127.0.0.1` on `JUSTUP_PORT` (default 8787). A reverse proxy must keep the browser's API same-origin. Private local storage uses a restrictive umask and mode-0600 database. The reviewed shared preview uses `JUSTUP_SHARED_STATE=true`, process umask `0007`, and an existing root-created setgid `02770` state directory; database, WAL and SHM files are `0660`. Only the API and queue UIDs belong to its state group. The model UID has no database access. Shared startup rejects a different directory mode or umask and does not create or change group ownership. Runtime secret files remain owner-only `0600`. The explicit `JUSTUP_ALLOW_LOCAL_HTTP=true` option permits local HTTP only for localhost or loopback testing.

Registration defaults to invitation-only with `JUSTUP_REQUIRES_INVITATION=true` and requires `JUSTUP_INVITE_CODE`. Explicit `false` enables public registration; only backend admission state authorizes it. `JUSTUP_MAX_ACCOUNTS` defaults to 30 (`none` explicitly removes the application cap). Accounts have no default expiry: `JUSTUP_ACCOUNT_TTL_MS` and `JUSTUP_ACCOUNT_EXPIRES_AT` can assign a persisted deadline to newly created temporary accounts. Session expiry defaults to seven days independently. See [accounts](../docs/auth.md). Both registration and login stay closed until these are configured: `JUSTUP_POLICIES_REVIEWED=true`, approved HTTPS `JUSTUP_PRIVACY_URL` and `JUSTUP_USAGE_URL`, and `JUSTUP_POLICY_VERSION`. This is a reviewed deployment decision; setting a flag does not itself constitute policy approval. Policy pages are static frontend routes. There is no policy JSON API.

The [processing admission guide](../docs/processing-admission.md) defines the shared account/visitor proof, exact locale policy maps, explicit fallback and bounded API-to-queue revocation. Existing signed-in sessions cannot bypass current policy or pending-deletion checks for private writes/provider work. Stored account reads, logout and safe deletion remain separately available.

Set immutable `JUSTUP_SOURCE_COMMIT` and `JUSTUP_BUILD_ID` for version reporting. The `product-draft-5` policies remain unreviewed. Supply stable random secrets of at least 32 bytes as `JUSTUP_CSRF_SECRET` and `JUSTUP_CURSOR_SECRET` through the protected preview runtime; never put values in commands, Git or a frontend bundle. Omitted secrets are process-local random values, suitable for isolated tests; restarting invalidates existing cursors and CSRF tokens until the next session read. Use the [credential guide](../docs/secrets.md) for runtime delivery.

Load an already reviewed private export with `node server/main.mjs --import /private/job-data/snapshot.json` using the explicit application database path and shared-state option where applicable. This operation opens only the public snapshot store and does not create authentication, run account cleanup or omit domain deletion hooks. This command prints only counts and a random import generation, then exits. It does not fetch, schedule, transfer or deploy anything. Import files are at most 64 MiB, each body at most 512 KiB, and the store retains at most 1,000 jobs plus 32 bounded import summaries. SQLite has a 1 GiB page ceiling; preview disk and aggregate process/resource enforcement belongs to the deployment contract. Keep storage and exports outside Git; SQLite files are ignored. The durable `job_source_identities` registry retains source ID, company ID, original discovery time and latest activity/reservation observation even when job evidence ages out; changing either identity field rejects the transaction. Older per-record evidence cannot reopen a later closure/reservation or replace newer content.

Jobs older than 14 days or with verification older than 24 hours are suppressed independently. Visitors receive only the 48-hour–14-day slice. Accounts receive eligible jobs within 14 days. Explicit inactive observations record when closure was observed; missing/failed refreshes remain unknown. Source descriptions and evidence hashes are internal only. Public DTOs expose structured fields and original links; the company catalogue does not infer official domains or claim board monitoring.

## Standalone feature composition

`JUSTUP_SERVICES_ENABLED=true` selects the fixed reviewed `server/composition.mjs` adapter. There is no module-path environment option or untrusted plugin loader. It exports synchronous `createApiServices(deps)` and `createApiReadiness({config,now})`; the executable passes those actual feature factories and readiness function to the core. If the adapter is absent, enabled startup fails. Its API role has no inference credentials or broker access. `JUSTUP_RUNNER_STATUS_PATH` selects an absolute heartbeat metadata file, defaulting to `runner-status.json` beside the database. The adapter verifies the exact source/build identity and a heartbeat at most 30 seconds old. Disabled or stale model capabilities stay unavailable without closing account login or deletion. Queue composition and heartbeat production are adapter-owned; resource and UID proof remain operations-owned.

## Extend the API

`await createApplication({config, now, serviceFactories, authFactory, logger})` returns `{server,store,feed,tasks,auth,services,close}`. `authFactory` is an isolated-test seam; normally it imports `createAuth` from `auth.mjs`. Each synchronous feature factory receives `{db,feed,tasks,config,now,beforePrivateDelete,afterPrivateTransaction,withPrivateTransaction}` and returns one service or an array. A service may implement:

- `capabilities`: object or zero-argument function reporting actual availability.
- `publicRoute(ctx)`: optional GET-only projection for published public data (for example a Hiring Wire edition). It runs before the account-required dispatch; no mutation uses this hook. Return `{status,body}` or null.
- `route(ctx)`: async or synchronous; return `{status,body}` when handled or null/undefined otherwise.
- `taskResult(task,ctx)`: return the safe accepted search/request or warning for its own task kind, undefined for other kinds. Return exactly one key: `{search}`, `{request}` or `{proposal}`. The public envelope is `{id,kind,status,createdAt,updatedAt,result,error}`; pending/running have null result/error, and failed tasks have a redacted `{code,message,retryable}` error. Raw task output is never exposed automatically. Do not place job DTOs or raw provider output in task responses.
- `deleteAccountData(ownerId)`: synchronous private cleanup inside the auth transaction, without another transaction or asynchronous work.
- `close()`: release sockets, timers and other owned resources before HTTP shutdown and SQLite close.

The fixed `live-results.mjs` service exposes its streaming hook only through the central HTTP boundary. Its active-search URL, prefix/removal reconciliation, cookie rechecks, opaque reconnect identities and bounded lifetime/backpressure are described in [live results](../docs/live-results.md). `intent.snapshot` reuses the canonical result path without pagination cursors, delivery-offset updates or speculative classifier refill; inactive tabs cannot schedule work through the stream.

The route context is `{method,path,url,body,viewer,accountId,requestId,db,idempotencyKey}`. `idempotencyKey` is null or the validated `Idempotency-Key` header (1–128 ASCII token characters); company acceptance must not substitute a body field for this header. `path` excludes `/api/v1`; `url` is a URL object. `viewer` is `auth.session(token)` with `{account:{id,username,expiresAt},expiresAt,access}`, or null. Private feature routes always receive a signed-in viewer; ownership comes from `accountId`. Mutation Origin, CSRF, rate and JSON checks run centrally before a service executes. Services must recheck domain authorization, revisions and limits. Feature errors use reviewed safe codes; unrecognized errors become a generic 500. No exception message or provider output reaches the browser or diagnostic logger.

`feed.eligibleJobs({viewer})` supplies internal eligible evidence in source-time descending, ID ascending order. Recheck it for every result page. `feed.publicJob(job)` is the allowlisted browser projection. `feed.list` cursors bind evidence generation, guest/account access and a ten-minute lifetime. Missing or stale imported evidence returns an empty `paused` page with `retryAfterMs:5000` and the validated input cursor (or null for a first page). Coverage reports `stale:true`, `state:"import_unavailable"`, nullable `verifiedAt` and the description `Imported listings need verification.` Cursor validation still runs before this pause. A refreshed import changes the generation and invalidates older cursors; restart without one. Fresh eligible zero remains `exhausted`. Public company methods expose imported and explicitly accepted identity/evidence. Accepted requested coverage does not claim working monitoring; reviewed official-domain aliases preserve the earlier public company ID without changing stored source posting identity. `coverage()` reports imported snapshot verification and staleness, never an unsupported coverage claim or hidden count.

`tasks.enqueue({ownerId,kind,requestKey,payload})` returns the existing task for an exact retry; a changed payload with the same owner/kind/key conflicts. Payloads are at most 16 KiB, output at most 64 KiB, at most 96 tasks exist and at most four pending/running tasks belong to one account. Terminal rows expire after 30 days when enqueuing. `claim({workerId,kinds,leaseMs})` allows one global running task and returns `leaseToken`; leases are 1–300 seconds. `heartbeat(id,leaseToken,leaseMs)` and `complete(id,leaseToken,{status,output,errorCode})` compare the live lease and return a boolean. Complete statuses are succeeded/warning/failed. `recover()` retries expired leases up to three attempts, then records safe terminal failure. Safe provider-down, timeout and rate-limit task errors have `retryable:true`; validation errors and unknown codes are not retryable. A worker must check lease ownership and resource/time limits before committing domain effects in the same database transaction. The queue alone does not make an external provider call exactly once.

`tasks.get(ownerId,id)` is internal and returns null for a different owner. `publicView(task,safeResult)` strips payload, raw output and lease details. `delete(ownerId,id)`, `cancel(ownerId,id)`, `cancelOwner(ownerId)` and `deleteOwner(ownerId)` deliberately open no transactions and invalidate late completion. The feature deletion hooks and task deletion compose with auth deletion atomically.

Health reports process readiness and a separate runner availability state. The core has no runner: its default runner identity is null and readiness false. Integrations inject `config.readiness()` and feature capabilities from the actual bounded runner/provider, and must verify them before release. `/version` reports source commit, schema version, immutable build identity, runner and import generation; missing values are null, never fabricated identities. The fixed API composition includes follows, preferences, viewed state, confirmed hidden counts, bounded SSE delivery, public company reports and Hiring Wire edition reads. Private processing requires the policy, deletion and auth-maintenance protections. Public catalogue, report and Wire GET routes create no visitor or task rows; only `/session` supplies the stateless ownership cookie used by a later admitted visitor search. The shared runner composes interactive search/company/matching work with Wire's weekly tick and foreground preemption; an unproven cleanup keeps its durable halt and private invocation state.

`reading-preferences.mjs` owns durable follows, negative unfollow choices, interface preferences and per-search options. See [reading preferences](../docs/reading-preferences.md) for exact DTOs, the explicit five-locale interface set and any-language/OR/intersection semantics. It injects the effective compiler configuration into both API and queue matching. Follow/option changes atomically bump affected search revisions and remove incompatible queued work without inference. Viewed state stays in the existing visitor/workspace service. Company acceptance publishes/reuses a public canonical catalogue identity and automatically follows it without overriding explicit unfollow.

`companies.mjs` also serves the bounded private followed/requested catalogue and the no-research known-company premium action. `company-progress.mjs` owns additive epoch-2 shared setup milestones; public projections expose only safe progress, while each private request reports that owner's current premium status. The [operator checklist](../scripts/company-requests/README.md) defines bounded private pending reads and revision-checked updates, with no configuration execution. Its queue recalculates aggregate premium ordering from current access. Live monitoring remains unavailable until a reviewed current-source receipt producer is implemented and qualified. The adjacent catalogue/progress suites own these real SQLite and local HTTP contracts, normally under one second with synthetic files and no provider.

`company-reports.mjs` serves keyless public report reads from guest-eligible structured listing samples and the existing published frozen source-history table. It never opens source files or queues work. The [company report guide](../docs/company-hiring-reports.md) defines sampled role/salary coverage, unknown periods, canonical identity, provenance and separate listing/history freshness. Its adjacent suite uses real SQLite and synthetic source/publication evidence, including the actual Python importer against a fake public source; it normally completes in under one second without providers.

Diagnostics are optional metadata-only callbacks: request ID, route category, status and duration. There is no raw query/body/IP/token logging. Abuse keys are ephemeral HMACs of the direct socket peer, with a bounded map and minute windows; forwarded headers are ignored. A reverse proxy needs its own trusted per-client limits so shared ingress cannot erase the effective user boundary. No durable diagnostic log or model trace is created by core code.

The fixed feature composition adds bounded private journey/execution metadata and an explicit operator-reviewed synthetic/redacted evaluation collection. [Product evidence](../docs/product-evidence.md) defines the events, incomplete cohort denominators, seven-day private retention, owner deletion/handoff and aggregate-only default CLI. There is no public telemetry route or automatic user-text sampling. The existing `/viewed` write reports an outbound activation; the metric is a client report of a source opening, never an application or hire. Reviewed evaluation cases and comparisons do not qualify a model or launch.

## Private deletion and recovery

Persistent deployments require precreated mode-0700 state and dedicated flat backup directories. Set `JUSTUP_PRIVATE_GENERATION_PATH` to the live UUID-plus-newline generation file and `JUSTUP_BACKUP_DIR` to the dedicated backup directory. The API does not create these recovery directories. The generation file cannot be inside the backup directory, and neither can the live database; dot-prefixed filenames do not bypass this boundary. Symlinks, nested directories and nonregular backup entries fail closed. With missing or unwritable recovery state, login and registration remain unavailable.

Before private deletion, the transaction owner creates `private-generation.pending` exclusively with mode `0600`, containing a version and random ownership token. It fsyncs the marker and state directory **before** rotating the generation. The marker remains present throughout the actual SQLite commit or rollback. The barrier then writes a new generation through a mode-0600 exclusive temporary file, fsyncs it, renames it over the live generation and fsyncs its parent; it purges the dedicated old backup files and fsyncs their directory. Generation rotation alone is insufficient: a concurrent SQLite backup can still contain pre-deletion rows until the writer commits.

Feature DELETE routes use `withPrivateTransaction(syncFunction)` and call `beforePrivateDelete()` inside the function before private SQL deletes. The wrapper commits or rolls back, then invokes `afterPrivateTransaction()`. Never await inside a database transaction. Account hooks remain synchronous inside auth's transaction; they never clear the marker themselves. HTTP completion/finally and auth maintenance call `afterPrivateTransaction()` only after the auth-owned transaction ends. Marker cleanup refuses while `db.isTransaction` is true and checks the marker's regular-file identity and ownership token before unlinking and fsyncing the state directory. It never clears another process's marker. A crash-retained or replaced marker fails closed and requires an explicit operator recovery decision; startup does not automatically erase it.

Backup and restore consumers must make a stable generation read with no pending marker both before and after taking or accepting the SQLite snapshot: generation read 1, require no pending marker, generation read 2, require equality. They reject missing or mismatched generations, and never restore the live generation or pending marker. A retained pre-deletion backup fails against the rotated live generation. Tests also copy the real SQLite database from a second process during an uncommitted deletion: that copy still contains the old private row and the new generation, while the pending marker correctly causes both consumer checks to reject it.

The explicit `node server/main.mjs --prepare-restored-db /private/restored.sqlite` command rejects the live database path and calls the auth-owned `invalidateAllSessions()` helper on the separate restored file. It prints `{schemaVersion:2,sessionsInvalidated:true,remainingSessions:0,sessionsDeleted}`. Only `JUSTUP_DB_PATH` (the live-path guard) is required; no runtime credentials, browser origin, feature services or account-retention cleanup run during preparation. It cannot restore a backup or its generation. Normal fully composed runtime startup invokes auth `cleanup()` once per minute with all feature deletion hooks; failures close authentication availability until a successful retry.

## Storage compatibility and launch contracts

Durable product tables use `justup_*`; existing stable `auth_*`, `access_*`, `job_source_identities` and `hiring_wire_*` names remain unchanged. The [explicit offline naming migration](../docs/schema.md) preserves all state and raises the application epoch to 2 atomically. Protected launchers and host switching compare actual SQLite with the selected immutable artifact. Epoch-1 snapshots require explicit forward migration before restored-session invalidation; there is no downgrade to epoch 1 or an API that invents account deadlines. Independent snapshot/search/heartbeat/source/ledger wire formats remain version 1.

[Backend design](../docs/backend-design.md) records accepted product behavior. Complete account, reading-preference, translated browser and live-delivery journeys remain launch gates. Do not activate real users merely because isolated runtime checks pass. The default JEV cumulative approval guard and existing preview filesystem, process, task and secret boundaries remain mandatory.

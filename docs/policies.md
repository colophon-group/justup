# Review Privacy and Usage

`/privacy.html` and `/usage.html` are static, unapproved **`product-draft-5`** notices. Their visible status, metadata and body attributes say **draft — review incomplete**; there is no effective date. The operator is **Viktor Shcherbakov**, contact **business@colophon-group.org**. A code merge, build or supplied contact does not approve the notices or authorize account/model activation or public sharing.

English uses `/privacy.html` and `/usage.html`. German, French, Italian and Spanish use `/privacy.de.html` / `/usage.de.html`, `/privacy.fr.html` / `/usage.fr.html`, `/privacy.it.html` / `/usage.it.html` and `/privacy.es.html` / `/usage.es.html`. All ten documents are unreviewed drafts. A translated file, browser-language detection or an English fallback does not approve admission in that language. Before admitting real users in any of these five interface locales, obtain review of the equivalent complete notice pair for that locale, or an explicit operator-approved fallback with recorded scope. No fallback is approved by this implementation.

The common facts, section inventory and English copy live in [policy content](../web/policies/content.ts). Typed German, French, Italian and Spanish copy must contain every key with the same shared-fact placeholders. The [renderer](../web/policies/render.ts) uses one escaped, script-free layout and common version/operator/review metadata. The [Vite plugin](../web/policies/vite.ts) serves these exact documents during development and emits ten HTML assets during a public client build, alongside local [policy CSS](../web/public/policies.css). It emits no notices into private SSR bundles. Brand, navigation and footer search links retain the notice language: `/#jobs` for English and `/{de,fr,it,es}/#jobs` for the other locales. Source remains under `web/` so credential-free frontend snapshots include it; generated `web/dist` files must not be committed. These completeness and delivery checks support review; they do not establish translation accuracy or operator approval.

The notices describe durable service behavior separately from temporary deployment settings. Account invitations, registration capacity, an optional temporary account deadline, snapshot availability and preview expiry are deployment constraints. They must not become product entitlements or imply that an unavailable product capability is complete. No invented corporation, address, jurisdiction or provider handling guarantee belongs in these pages.

## Check temporary deployment settings separately

Accounts are durable by default: `accountTtlMs` and `accountExpiresAt` default to `null`, and `/session.user.expiresAt` is `null` when no temporary deadline applies. An optional relative lifetime or absolute deadline is resolved and stored only when a new account is registered; changing deployment configuration does not alter existing account deadlines, and signing in does not extend them. Accounts remain until user deletion unless an explicitly configured and disclosed temporary deadline applies. The default registration capacity is 30, with an optional uncapped configuration, and invitation access defaults on. These code defaults do not prove the selected deployment settings. Read back capacity, invitation access, any temporary account deadline and deployment expiry before issuing invitations; account lifetime is independent of deployment expiry unless an explicit account deadline is configured.

Sessions use `sessionTtlMs`, a configurable fixed lifetime with a seven-day default, bounded by any stored account deadline. `/session.expiresAt` reports the separate session deadline and is `null` for guests. Guest request-protection cookies last one hour. Verify and disclose the actual session lifetime before activation. Local matching/diagnostics have seven-day limits, and recovery permits at most two SQLite backups with a seven-day usable age.

Read back these values from the selected deployment before approval. They are not subscription rules. A temporary deadline must be disclosed explicitly; an account must not silently change from durable to expiring. A changed configuration requires matching disclosure review and cannot inherit approval from a notice for different settings. Record audience, fixed deployment expiry and independent teardown in the deployment evidence, keeping those controls separate from durable product data and behavior.

## Verify each enabled model profile

Search interpretation and company discovery have different tool requirements. The intent parser remains tool-free. Company discovery requires native web search/browsing; its exact supported profile, input handling and activation evidence are not settled. Do not infer the company profile’s tool catalogue or privacy handling from the intent profile.

The currently implemented company path uses broker-managed bounded official-page fetches with model-supplied identity evidence; it is not proof of a native-web discovery path. Its current bounds are: known imported identity, zero inferences; explicit website, at most two trusted official pages and one grounded call; name-only input, at most one private unverified domain proposal (512 observed tokens), then official-page fetch and one grounded call. The combined output/deadline bound is 6,000 tokens/60 seconds. Published URLs must come from fetched evidence and the name must be grounded in title, heading or visible text. Those limits describe the current broker implementation, not an approved native-web profile. An unverified proposal is never a confirmed public identity.

Before enabling native-web company discovery, inventory the company input and generated search/browse inputs sent to OpenAI, default account/request metadata, provider-side retention and processing, and requests to outside sites. Confirm which recipients and countries actually apply; do not guess them. Publish matching disclosures and verify evidence grounding, ambiguity handling, token/deadline limits, quality and cost against the exact implemented profile. The public draft keeps native-web discovery explicitly conditional and disabled pending these checks.

Every enabled profile needs its own exact pinned model/CLI/configuration identity, complete advertised tool catalogue, operating-system/filesystem/network boundary, invocation log/cache/trace retention and failure/crash cleanup evidence. Also verify provider/subscription/default-account metadata, schema/evidence validation, held-out quality, latency and budget. The intent profile requires an empty tool catalogue; the company profile must prove only its approved native-web tools are available. Neither source tests nor zero observed tool calls establish these deployment/provider facts. Never claim zero provider retention. TypeSafe/JEV remains a separate residual-matching recipient and requires its own verified configuration and spend guard.

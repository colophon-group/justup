# Configure policy and processing admission

All five interface policy pairs remain unapproved `product-draft-5` drafts. Keep `JUSTUP_POLICIES_REVIEWED=false`. Neither a configuration example nor passing tests constitutes operator review or authorizes activation.

## Bind approval to the served language

The API accepts trusted operator configuration, without a settings or consent API:

- `JUSTUP_POLICY_LOCALES` is a JSON object keyed only by `en`, `de`, `fr`, `it`, `es`. Each entry has exactly `{privacyUrl,usageUrl,version,reviewed}`. `reviewed` is a boolean and must be `true` for approval of an explicit entry; version is a bounded identifier.
- URLs must equal the configured frontend origin plus `/privacy.html` and `/usage.html` for English, or `/privacy.de.html` and `/usage.de.html` for German, with corresponding `fr`, `it`, `es` suffixes. HTTPS is required outside explicit localhost HTTP tests. Query strings, fragments, other origins and mismatched language paths are rejected.
- `JUSTUP_POLICY_FALLBACKS` optionally maps a requested supported locale to a different explicitly reviewed locale entry. Record operator approval for that exact fallback before configuring it. Fallbacks do not chain.
- The global reviewed flag remains the kill switch for every locale. `JUSTUP_PRIVACY_URL`, `JUSTUP_USAGE_URL`, `JUSTUP_POLICY_VERSION` configure English metadata with the exact same-origin `/privacy.html` and `/usage.html` paths. When no explicit English entry exists, valid legacy metadata supplies its locale approval configuration without a separate per-locale `reviewed` field. Admission still requires global review and the same exact asset proof as an explicit English locale entry. Swapped, arbitrary, localized or decorated URLs cannot supply approval. This configuration never approves the other four locales or creates a fallback.
- `JUSTUP_POLICY_ASSET_PROOF` is an operator-supplied JSON object with exactly `{origin,sourceCommit,assetsSha256,locales}`. The origin and source commit must match the trusted frontend origin and candidate source. `locales` maps supported page languages to exactly `{version,privacySha256,usageSha256}`. Hashes are lowercase SHA256 values from the reviewed retained frontend inventory. The API never creates this proof. Every requested locale, including English and an explicit fallback, remains unreviewed without a matching proof for its exact served policy version. For an explicit fallback, the binding belongs to the reviewed target pair. Asset proof does not replace global review or matching locale approval configuration.

Without an explicit entry, valid legacy English metadata or a configured fallback, a locale resolves to its canonical URLs and `product-draft-5`, with `reviewed:false`. An explicit locale entry takes precedence over legacy English values, including an unreviewed entry. Each approved locale retains its own exact URLs/version; there is no inferred translation equivalence.

Verify static policy bytes before enabling processing: run `scripts/preview-verify.py` with `--mode policies`, the candidate backend `--manifest`, retained frontend `--frontend-release`, fixed `--base-url`, operator-reviewed `--policy-asset-proof` and a new `--report` path. This mode reads only the exact policy pages and works while review flags are off. It compares served bytes with both the retained asset inventory and the supplied reviewed hashes, and checks HTML language, policy kind and version. Missing pages, a single-page-app fallback, swapped pages, stale versions or a changed candidate fail. The report repeats the supplied proof; it never manufactures approval from the observed pages. Installing a proof or passing this byte check does not approve draft notices.

After explicit operator review, full `--mode preview` requires the same proof and retained frontend identity. It requests all five locale sessions with `Accept-Language`, checks each approved locale/fallback against the verified page language, URLs and version, and requires every proof locale to be admitted. English metadata also requires exact served-page verification for release. A policy hash, artifact, origin, candidate source or version change requires a new reviewed binding. No verifier command changes flags, supplies credentials, starts providers or activates users. Partial `--mode policies` inspection remains available before approval; configuring one reviewed locale does not approve another or settle the release's required language scope.

`session.policies` preserves `privacyUrl`, `usageUrl`, `version`, `reviewed` and adds `locale` (requested presentation language), `reviewedLocale` (reviewed page language, otherwise null), and `fallback` (true only for an admitted explicit fallback). The browser must evaluate these fields for the effective interface language. There is no separate policy endpoint.

## Resolve presentation consistently

An explicit route sends one `X-Justup-Locale` header containing exactly `en`, `de`, `fr`, `it` or `es`. It selects the current request before saved or browser preferences and never saves a preference. Invalid, duplicated or comma-separated values return 400. Selecting a locale cannot bypass its policy approval. For an authenticated account without that header, resolution is its saved interface override, then bounded `Accept-Language`, then English. A null saved preference means browser/default and ignores any earlier guest cookie. Guests resolve the explicit device cookie, then `Accept-Language`, then English. The fixed five-value `justup_interface_locale` cookie is frontend-owned: set it only after an explicit language choice, with `Path=/; SameSite=Lax; Max-Age=31536000` and `Secure` on HTTPS; clear it for browser/default mode. It contains no identifier and does not allocate a visitor. Login never copies it into an account preference or another account. Forward `X-Justup-Locale`, `Cookie` and `Accept-Language` through the same-origin API proxy.

The API accepts at most 512 header characters and 16 language candidates, canonicalizes standard tags to the supported base language, and stores no browser-language list. Duplicate/invalid locale-cookie values do not select a locale. An explicit `presentationLocale` on a submission must equal this resolved language. The queue persists only the selected enum and a hash of its exact approved policy metadata. Generated search titles/reasons and model-generated company clarification use that selected language; queries, requirement text, company names, canonical IDs, URLs and source evidence retain their original content.

## Use one processing proof

`server/processing-admission.mjs` owns one SQLite row, `justup_processing_admission`, for accounts and visitors together. Startup renames the existing `justup_visitor_admission` table in place, preserving its row, then adds the locale scope column. A legacy row without locale scope cannot admit processing. No private account, search or task rows are reset.

API startup disables the previous proof before serving requests. Fully composed synchronous auth/visitor maintenance then publishes current availability. The proof binds source commit, build identity, exact approved locale metadata and asset hashes, private deletion generation and check time. The internal policy key includes the complete asset binding so a queued task cannot outlive a changed proof. Writes occur on changed state or after 30 seconds; maintenance runs every 60 seconds. Queue proofs expire at 90 seconds. An independent queue reader never refreshes or repairs the API's proof. Revocation propagation is bounded by those intervals; it is not instantaneous across processes. Restarting the API with closed policies immediately withdraws its persisted proof before accepting routes.

Before each dispatch and again after waits/before transaction commit, account and visitor tasks require the same approved locale key, current owner/entitlement, a live lease and applicable revision/evidence fences. Old tasks without the new policy key cannot execute through the composed authority. Provider unavailability is separate: it does not revoke login, logout, deletion, stored search/request/workspace/preferences reads or the ordinary eligible feed.

Each processing check also performs a direct stable private-generation read: read generation, require no pending marker, read generation again and require equality. A live/foreign/crash-retained pending marker closes processing immediately, even when the proof is young. This code never clears or repairs that marker. An expired/wrong-build proof, missing generation, unreviewed locale or changed exact policy metadata prevents inference and new private processing effects. HTTP reports `policy_unavailable`, `deletion_unavailable` or maintenance `dependency_unavailable`; queued work reports non-retryable `processing_unavailable` separately from provider/network failures. Refresh the session before offering a new submission.

Safe logout and deletion remain available during a policy pause, subject to their own session, CSRF/password and deletion protections. Stored account reads remain owner-bound; result pagination and SSE are processing paths because they can update cursors or enqueue matching. Visitor processing reads retain their policy gate. A pending deletion marker can also prevent a new deletion until operator recovery makes the deletion barrier safe.

## Verify before release

Run `node --test server/policies.test.mjs server/visitor.test.mjs server/model-broker.test.mjs` and the complete server suite with pinned Node 24.22.2. The primary regression uses real SQLite/HTTP and a persisted account session across policy-closed restart. Other contracts cover pending deletion, independent queue expiry/wrong build, exact locale key changes, post-provider account/visitor revocation, preserved cleanup/stored reads, enum/header precedence and zero unauthorized model/JEV/private decision writes. Providers are fake.

Run `python3 scripts/preview-operations.test.py` for immutable packaging and the launcher-to-actual-Node locale configuration compatibility test. These source checks do not establish served page bytes, operator approval, deployed proxy headers, provider handling, cleanup/restore rehearsal or complete release journeys. Record those against exact compatible frontend/API/runner artifacts before real-user activation.
